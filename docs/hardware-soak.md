# v1.0 hardware soak

Issue #177 is a real-hardware release gate. Host pytest coverage is useful, but
it cannot prove that ESP32 flash writes, watchdog resets, SoftAP provisioning,
and boot-loop recovery work together with real timing and power behavior.

`scripts/hardware_soak.py` runs the destructive checks against one connected
classic ESP32 and writes a secret-free `report.json` plus serial/tool logs. It:

1. records the commit and device information;
2. takes a private full-device backup;
3. starts a genuinely blank SoftAP provisioning boot and pauses while the
   operator joins the AP and submits the web form;
4. applies a checksummed manifest through the device's real HTTP OTA client,
   verifies the flash swap and `.ota_bak`, rolls back, and byte-compares the
   restored target;
5. installs a temporary watchdog probe, observes physical watchdog resets and
   boot-loop safe mode over serial; and
6. restores the original filesystem and removes the credential-bearing backup.

The runner restores the board after a failure too. If restoration itself fails,
it leaves the mode-0700 `.device-backup` inside the artifact directory and says
so in `report.json`; keep that directory private and use `tinker.py restore`
after fixing the serial connection.

## Prepare the OTA fixture

Build and publish a release-candidate manifest to an HTTP(S) location the ESP32
can reach. At least one manifest entry must replace an existing device file; use
that file as `--ota-target`. Every entry must contain the SHA-256 generated by
`ota build`.

```shell
python tinker.py ota build \
  --version 1.0.0-rc1 \
  --base-url https://firmware.example.test/1.0.0-rc1 \
  main.mpy app/services/runtime.mpy

python tinker.py ota validate \
  dist/ota/1.0.0-rc1/manifest.json \
  --files-root dist/ota/1.0.0-rc1
```

Upload `dist/ota/1.0.0-rc1/` without changing its paths or contents. Do not put
WiFi, MQTT, CDN, or device credentials in the command line or evidence folder.
The runner refuses `device_config.json` as the OTA target so a credential file
cannot be copied into the evidence bundle.

## Run

Stop any serial monitor first, then run from the repository root:

```shell
python scripts/hardware_soak.py \
  --port /dev/cu.usbserial-21440 \
  --ota-manifest-url https://firmware.example.test/1.0.0-rc1/manifest.json \
  --ota-target main.mpy
```

The provisioning phase asks for two explicit confirmations. Join
`Microweaver-Setup`, open `http://192.168.4.1`, submit the form, and type `PASS`
only after the page says `Credentials saved. Connected!`. Credentials remain on
the board and in the private backup; they are never copied into the report.

To rerun only one phase:

```shell
python scripts/hardware_soak.py \
  --port /dev/cu.usbserial-21440 \
  --stages recovery
```

The default watchdog capture is 20 seconds. Increase `--watch-seconds` on a
board with a longer boot delay.

After the point checks pass, run the 24-hour capture against the restored
release candidate. During the capture, perform several planned WiFi outages,
broker outages, and power cycles, and note their times so every reset in the log
can be explained:

```shell
python scripts/hardware_soak.py \
  --port /dev/cu.usbserial-21440 \
  --stages burnin \
  --burn-in-hours 24
```

## Pass criteria and burn-in

The automated reports must show `passed` for provisioning, OTA, recovery, and
burnin, and `restored: true`. Keep the reports and logs as release evidence.
Correlate the burn-in serial capture with MQTT health output and the planned
WiFi outages, broker outages, and power cycles.

Do not tag v1.0 if there are unexplained resets, heap decline, failed reconnects,
incorrect reset reasons, orphan `.ota_new`/`.ota_bak`/state files, a failed
restore, or any phase marked failed.

# v1.0 hardware soak

Issue #177 is a real-hardware release gate. Host pytest coverage is useful, but
it cannot prove that ESP32 flash writes, watchdog resets, SoftAP provisioning,
and boot-loop recovery work together with real timing and power behavior.

`scripts/hardware_soak.py` runs the destructive checks against one connected
classic ESP32 and writes a secret-free `report.json` plus serial/tool logs. It:

1. records the commit and device information;
2. takes a private full-device backup;
3. starts a genuinely blank SoftAP provisioning boot, pauses while the operator
   joins the AP, then fetches and submits the real web form with credentials
   read only from the private backup;
4. applies a checksummed manifest through the device's real HTTP OTA client,
   verifies the flash swap and `.ota_bak`, rolls back, and byte-compares the
   restored target;
5. installs a temporary watchdog probe, observes physical watchdog resets and
   boot-loop safe mode over serial; and
6. restores the original filesystem and removes the credential-bearing backup.

The runner restores the board after a failure too. If restoration itself fails,
it leaves the mode-0700 `.device-backup` inside the artifact directory and says
so in `report.json`; keep that directory private and use `tinker.py restore`
after fixing the serial connection.

The initial backup downloads into `.device-backup.partial` and is promoted only
after every device file arrives. A raw-REPL failure triggers one automatic hard
reset and readiness check before retrying from an empty staging directory. An
incomplete backup is deleted and is never used by the restore path.

## Run the automated local OTA fixture

For the flash-write and rollback gate, the runner can generate and host its own
temporary fixture. The host and ESP32 must be on the same LAN, and the host
firewall must allow the temporary inbound connection:

```shell
python scripts/hardware_soak.py \
  --port /dev/cu.usbserial-21440 \
  --stages ota \
  --ota-local-fixture
```

The runner discovers the host IPv4 address selected by the default route,
binds an available port on that address, and serves only an in-memory manifest
and `boot.py`. It reads the installed `boot.py`, appends a harmless unique
comment, computes the SHA-256, and keeps the server alive only while the ESP32
downloads the fixture. On VPN or multi-interface hosts, choose the address on
the ESP32's LAN explicitly:

```shell
python scripts/hardware_soak.py \
  --port /dev/cu.usbserial-21440 \
  --stages ota \
  --ota-local-fixture \
  --ota-host-ip 192.168.1.50
```

This proves real HTTP download, checksum verification, filesystem staging and
swap, `.ota_bak` creation, state persistence, explicit rollback, exact-byte
restoration, and removal of the staged/backup/state files. It does not reboot
into the changed payload and does not exercise production DNS, TLS, or CDN
configuration; keep the hosted cycle below as a separate release-candidate
check when those boundaries matter.

## Prepare a hosted OTA fixture

Build and publish a release-candidate manifest to an HTTP(S) location the ESP32
can reach. At least one manifest entry must replace an existing device file; use
that file as `--ota-target`. Every entry must contain the SHA-256 generated by
`ota build`.

```shell
python tinker.py ota build \
  --version 1.0.0-rc1 \
  --base-url https://firmware.example.test/1.0.0-rc1 \
  boot.py

python tinker.py ota validate \
  dist/ota/1.0.0-rc1/manifest.json \
  --files-root dist/ota/1.0.0-rc1
```

Upload `dist/ota/1.0.0-rc1/` without changing its paths or contents. Do not put
WiFi, MQTT, CDN, or device credentials in the command line or evidence folder.
The runner refuses `device_config.json` as the OTA target so a credential file
cannot be copied into the evidence bundle. Use a changed UTF-8 text payload such
as `boot.py`; the current on-device OTA downloader is text-based and should not
be used for compiled `.mpy` payloads until it supports binary response bodies.

## Run

Stop any serial monitor first, then run from the repository root:

```shell
python scripts/hardware_soak.py \
  --port /dev/cu.usbserial-21440 \
  --ota-manifest-url https://firmware.example.test/1.0.0-rc1/manifest.json \
  --ota-target boot.py
```

The provisioning phase requires an explicit `PROVISION` confirmation before it
removes the backed-up config. Join the open `Microweaver-Setup` network. Press
Enter to let the runner fetch and submit the form using the WiFi values held in
its mode-0700 backup. If you submitted the browser form yourself and already see
`Credentials saved. Connected!`, type `DONE` instead so the runner skips a
duplicate HTTP request. Both paths verify the saved file over serial. Credentials
are never printed, passed on the command line, or copied into the evidence
report.

To rerun only one phase:

```shell
python scripts/hardware_soak.py \
  --port /dev/cu.usbserial-21440 \
  --stages recovery
```

The default watchdog capture is 20 seconds. Increase `--watch-seconds` on a
board with a longer boot delay.

After the point checks pass, run the 24-hour capture against the restored
release candidate. During the capture, perform several planned WiFi outages,
broker outages, and power cycles, and note their times so every reset in the log
can be explained:

```shell
python scripts/hardware_soak.py \
  --port /dev/cu.usbserial-21440 \
  --stages burnin \
  --burn-in-hours 24
```

## Pass criteria and burn-in

The automated reports must show `passed` for provisioning, OTA, recovery, and
burnin, and `restored: true`. OTA evidence must show different before/applied
hashes, matching expected/applied hashes for a local fixture, matching
before/restored hashes, and no remaining `.ota_new`, `.ota_bak`, or state file.
Keep the reports and logs as release evidence. Correlate the burn-in serial
capture with MQTT health output and the planned WiFi outages, broker outages,
and power cycles.

Do not tag v1.0 if there are unexplained resets, heap decline, failed reconnects,
incorrect reset reasons, orphan `.ota_new`/`.ota_bak`/state files, a failed
restore, or any phase marked failed.
